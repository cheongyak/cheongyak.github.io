## 1. 기존 QA가 왜 놓쳤나

| 질문 | 2026-10-02 이전 상태 | 결과 |
|---|---|---|
| A. 필드를 하나씩만 검사했나 | 예. 정답 데이터(golden)·공고문 대조·불변식(invariants.py)은 값 하나가 원문과 같은지, 범위 안인지 | 거주의무가 null(모름)인 것은 '값 없음'이라 오류로 안 잡힘 |
| B. 판정끼리 비교했나 | 일부. consistency.cjs(카드·상세·필터 판정 묶음), sp_text.cjs(특공 문구) | 자금 플랜·전세 결과는 대상 밖 |
| C. 원천 ↔ 파생 관계 | 아니오. jeonseCheck 는 residenceDuty 를 읽지만, 같은 값을 칩은 `L.residenceDuty ? … : '없음'`(null → 없음), 주의 문구는 `== null`(null → 있을 수 있음)로 따로 해석 | 값 하나가 화면 세 곳에서 서로 다른 사실이 됨 |
| D. 화면끼리 비교 | 판정 결론만. 자금 플랜·상세 문구·상태(마감)는 비교 안 함 | 마감 공고 상세가 '신청 가능'만 보임 (162주택형) |
| E. 다른 기능 결과끼리 충돌 | 검사 없음 | '전세 조건부' ↔ '거주의무 있을 수 있음' |
| F. 의존 사슬 | 문서·검사 없음 | 상한제 → 거주의무 → 전세 → 자금 계획 → 카드 '자금 가능' 사슬 중간(거주의무)이 모름이어도 끝(자금 가능)은 확정으로 보임 |
| G. 한 조건이 결과를 무효화 | 검사 없음 | 마감이 '신청 가능'을, 거주의무 모름이 '전세 계획'을 무효화하는지 안 봄 |

구조적 원인(패턴, 20항):
1. **모름(null)을 거짓으로 읽는 코드** — JS 의 `x ? … : …` 가 null 과 0 을 같게 본다. 같은 필드를 화면마다 따로 해석.
2. **기능별로 따로 만든 결과** — 전세 판정(jeonseCheck)·칩·시나리오·카드 문구가 각자 조건을 다시 계산. 상태(모름)가 다음 단계로 전파되지 않음.
3. **상태 축(마감 등)과 판정 축의 관계 미정의** — 판정 함수는 '자격'만 보고, 접수 상태는 목록 정렬에만 쓰였다.
4. **원문 형식 변화** — 공고문 첫 쪽 표('단지 주요정보')를 문장 규칙만으로 읽으려 해서 표 모양이면 모름이 됨.

## 2. 두 계층

- **LEVEL A — 필드·데이터 검증**: 정답 데이터(tests/golden), 공고문 대조(app/crosscheck.py), 불변식(tools/qa/invariants.py), 시세 원자료(market_check).
- **LEVEL B — 교차 규칙·의미 검증**: 이 문서의 규칙(cross_rule.cjs) + 화면 결론 일치(consistency.cjs) + 특공 문구(sp_text.cjs) + 공급유형 표시(supply_type.cjs).

사실 상태는 세 가지로 나눈다: **CONFIRMED**(공고문·공식자료로 확인), **NOT_APPLICABLE**(없음으로 확인), **UNKNOWN**(확인 못 함).
UNKNOWN 이 중요한 결과에 영향을 주면 결과도 '확인 필요'가 된다(17항). 이 검사는 법률 판단을 새로 만들지 않고, 확인된 사실과 서비스가 보여 준 결과가 충돌하는지만 본다(16항).

```
[공고문 단지 주요정보 표] ─ 분양가상한제 ─┐
                       └ 거주의무기간 ───┼→ 거주의무 상태(CONFIRMED/N.A./UNKNOWN) → 전세 상태(ok/cond/check/no) ─┬→ 자금 플랜 칩·주의 문구
[수도권·규제지역(청약홈)] ────────────────┘                                                                   ├→ 전세 시나리오 '가능/부족/확인 필요'
                                                                                                             ├→ 기본 계획(전세/잔금대출) → 부족분 → 카드 '자금 가능(전제)'
                                                                                                             └→ 상세 '자금 (전세|대출) N 부족'
[청약홈 공급유형·HOUSE_SECD] → 공급 구분(일반/무순위/재공급) → 자격 규칙(통장·세대주·거주지) → 내 판정(eligibility·spJudge) → eligBucket → 카드·상세·필터
[청약홈 일정] → statusOf(접수 예정/중/마감) ─┬→ 목록 정렬·숨김
                                           └→ 상세 맨 위(마감이면 '접수 마감', 판정은 참고)
[공고문 소득·자산 표] → 특공 단계 → '가능/불가' → 특공 문구(뽑는 방식·약 N세대)
```
중간 값이 바뀌면(수집이 다시 읽거나 화면 코드를 바꾸면) 매 수집·화면 변경 때 cross_rule.cjs 가 끝 결과까지 다시 본다.

## 6. 모순 행렬 (6항, 주요 조합)

| 조합 | VALID | CONFLICT | CONDITIONALLY VALID | UNKNOWN |
|---|---|---|---|---|
| 거주의무 × 전세 | 없음 + 전세 가능 | 있음 + 전세 '가능' | 있음 + 조건부(한 번 2년) | 모름 → 전세 '확인 필요' |
| 상한제 × 거주의무 | 수도권 상한제 + 0~5년 | 상한제 아님 + 거주의무 > 0 | 상한제 + 없음(최초 공고가 시행 전) | 상한제 + 모름 |
| 마감 × 신청 가능 | 접수 중 + 가능 | 마감 + '신청 가능'만 | 마감 + 참고 판정 | — |
| 유주택 × 국민주택 | 불가 | 가능 | — | 주택 수 미입력 → 확인 필요 |
| 유주택 × 민영 추첨 | 비규제 1주택 추첨제 가능 | — | 규제지역 1주택 처분 조건 | — |
| 소득 × 특공 | 기준 이하 + 가능 | 초과 + 가능 | 출산 완화 구간 → 확인 필요 | 소득 미입력 → 확인 필요 |
| 자산 × 특공 | 기준 이하 + 가능 | 초과 + 가능 | 완화 구간 → 확인 필요 | 미입력 → 확인 필요 |
| 필요 자금 × 내 자금 | 부족분 0 + 가능 | 부족분 > 0 + '자금 가능' | 대출·전세 전제 '자금 가능(전제)' | 시세 모름 → 대출 한도 추정 |
| 마진 × 자금 | 마진과 자금을 따로 표시 | '마진 있음' = '자금 가능'처럼 표현 | — | — |
| 불법행위 재공급 × 무순위 | 원천 = 표시 | 재공급을 무순위로 | — | — |
| 공공 × 민영 | 하나만 | 둘 다 | — | — |
| 지난 공고(잠금) × 새 수집 | 잠금 값 유지 | 새 수집이 덮어씀 | — | — |

## 8. 출시 차단 (22항)

매 수집(collect.yml)·화면 변경(verify.yml)에서 실행하고, CRITICAL·HIGH 충돌이 1건이라도 있으면 `docs/verify-status.json` 의 `ok` 가 false → Actions 실패·이슈.

## 9. 새 기능 완료 조건 (12·24항)

새 기능을 올리기 전에 '이 기능이 기존 결과를 바꿀 수 있는가'를 적고, 영향 받는 결과에 대한 교차 규칙을 이 문서와 cross_rule.cjs 에 추가한다.
- 새 데이터 필드: CONFIRMED / NOT_APPLICABLE / UNKNOWN 을 구분해 저장하고, 화면에서 null 을 `x ? … : …` 로 읽지 않는다.
- 새 판정·계산: 그 결과를 무효화할 수 있는 조건(마감·모름·불가)을 찾아 규칙으로 등록한다.

## 10. 아직 못 하는 것

- 챗봇 답변과 화면의 교차 검사 (챗봇은 미리보기 단계, 답은 서버에서 생성).
- 지난 공고(보관) 화면의 교차 검사 — 보관 자료에는 자금 계산 필드가 없어 판정 축만 봄(pastjudge.cjs).
- 전매제한 × 매도: 화면에 '매도 가능' 표현이 없어 해당 없음. 표현을 만들면 규칙을 추가한다.
